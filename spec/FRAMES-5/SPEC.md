# FRAMES-5: Text layout

Status: accepted

## Summary

Text is laid out by resolve with real fonts: the face chosen by family, weight and style, a title's runs styled, tracking, kerning, OpenType features and baseline shift, lines broken and wrapped, right-to-left and mixed-direction text ordered by the Unicode Bidirectional Algorithm, lines set horizontally or vertically by a writing mode, runs shaped by the shaping provider, line limits, and the characters, words and lines laid out text is split into, with where each character lies.

## Motivation

If renderers laid out text, the same title would wrap differently on each, a lower third would end at a different place on each, and a frame measured from its content would not match what is drawn. Resolve writes glyph runs, so every renderer draws the same lines. A title often mixes looks inside one paragraph (a name in bold and a role in regular weight, one word in another colour), and runs give that as data, each in a named style, without a markup syntax to escape.

Every NLE titles Arabic and Hebrew, and a title in a left-to-right language often holds a name or a quotation in one of them. The order a line's glyphs are drawn in is decided between shaping and line layout, which are frames's own, so neither a pack nor an extension can add it: an extension that wrote the glyphs of a reordered line as text would break the words, the units and the ranges every report names. Holding the text in the order it is read everywhere but where glyphs are placed keeps every rule that reads text, from line breaking to a reveal by word, one rule for every script.

Chinese, Japanese and Korean titles are set in vertical lines in every NLE's vertical type tool. A vertical line is more than glyphs stacked down a column: its punctuation takes vertical forms (the corner brackets turned, the ideographic comma and full stop at the top right of their cells, the prolonged sound mark running down), which a face gives only to text shaped in vertical layout, and its Latin words and digits lie on their sides. An extension that stacked one title per character from what `evaluate` reports would set every one of those marks in its horizontal form, and its column would be no line, so `width`, `align`, `lineHeight` and a reveal by line would not reach it. Which axis glyphs are placed along is decided between shaping and line layout, which are frames's own, and holding a writing mode to that choice alone keeps every rule of this spec one rule in both.

## Rules

Text is laid out by resolve, with real fonts, so line breaks, faces, glyphs and every title's box are part of the resolved document and are the same on every renderer. Where a title's tracking, line height or background takes keyframes, evaluation places its glyphs and lines and sizes its box at each instant from that layout ([Spacing](#spacing), [Lines](#lines)).

### Runs

A title's text ([FRAMES-11](../FRAMES-11/SPEC.md)) is a string or a list of runs:

```json
"title": [ { "text": "Ana Ruiz", "style": "name" }, { "text": "\nDirector of photography", "style": "role" } ]
```

- A string is one run in the clip's `style`.
- A run is `{text, style}`. `text` is a string. `style` names a theme text style ([FRAMES-22](../FRAMES-22/SPEC.md)) and is optional: without it the run is in the clip's `style`. A style a run names that the theme in effect does not hold stops.
- A run's style gives that run its character attributes: `font`, `size`, `weight`, `italic`, `tracking`, `kerning`, `features`, `baselineShift`, `color`, `stroke`, `highlight` and `underline` ([FRAMES-22](../FRAMES-22/SPEC.md), [below](#highlights-and-underlines)), with the title's `character` merged over them ([FRAMES-11](../FRAMES-11/SPEC.md)). Every other attribute is a paragraph attribute and comes from the clip's `style`, with the title's `paragraph` merged over its `direction`, `align`, `lineHeight` and `background` ([FRAMES-11](../FRAMES-11/SPEC.md)): `placement`, `offset`, `direction`, `align`, `lineHeight`, `lines` and `background`. A run style's paragraph attributes are not read.
- The runs are laid out as one text, in order. A run's text may hold `\n`, and a line may hold parts of several runs.
- **Line endings are read as `\n`.** In a title's text, its arguments applied, each CR LF (U+000D U+000A), CR (U+000D), next line (U+0085), line tabulation (U+000B), form feed (U+000C), line separator (U+2028) and paragraph separator (U+2029) becomes one `\n` before anything else reads it, and a CR LF whose CR ends one run and whose LF begins the next becomes one `\n` in the run of its CR. These are the line endings UAX #14 breaks at, so every rule of this spec that names `\n` holds for each of them, and the ranges of a title's text count the scalars of the text so read ([Units](#units)), which is the text the resolved document writes ([FRAMES-19](../FRAMES-19/SPEC.md)).
- **A grapheme cluster (an extended grapheme cluster of UAX #29) is never split over runs**, since a character set in two styles is no one character: a cluster that a run boundary falls inside takes the style of the run its first scalar is in, and its later scalars are set and shaped with that run.
- An empty list of runs stops, since it is a title with nothing to show.

### Faces

- A style's family is the first family in its `font` list, or in the theme `font` when it has none, that its pack carries ([FRAMES-17](../FRAMES-17/SPEC.md)) or the machine has installed. A list with no family on the machine stops, naming the families.
- Its face is chosen among that family's faces by the font matching of CSS Fonts 4, with `font-stretch: normal`, the style's `italic` as `font-style` and its `weight` as `font-weight`. Width is narrowed first: the faces of normal width, else the narrower ones from the widest down, else the wider ones from the narrowest up. Then style: for `italic`, italic faces, else oblique ones, else upright ones; otherwise upright faces, else oblique, else italic. Then weight: a weight from 400 to 500 takes the nearest face from it up to 500, else the nearest below it, else the nearest above 500; a lighter weight takes the nearest at or below it, else the nearest above; a heavier one the nearest at or above it, else the nearest below. A face's width, style and weight are those its font file declares in its OS/2 table, as CSS reads them. So a family without a 300 face sets `light` text in its regular face, as a browser does.
- `italic: true` in a family with neither an italic nor an oblique face is set in its upright face, as the matching above gives it and a browser sets it. frames synthesises no weight and no slant, as CSS `font-synthesis: none`.
- Characters the face lacks fall back as CSS falls back: to the later families of the style's `font` list in order, each face chosen by the matching above, and then to a face the shaping provider finds on the machine for the style's weight and italic. The resolved document keeps the face it found, as it keeps recognised text ([FRAMES-21](../FRAMES-21/SPEC.md)).
- **A fallback face is chosen for each grapheme cluster, never for part of one**: a cluster is set in the first of those faces that has a glyph for every scalar of it that is not a `Default_Ignorable_Code_Point` of Unicode (a variation selector, a zero width joiner or non-joiner, a word joiner), and one that none of them has whole in the face the shaping provider finds for it. A default ignorable scalar takes no part in the choice, since a face maps it in a table of its own, as an ideographic variation selector is, or not at all, and a shaper sets it with the scalars beside it or as nothing. A zero width non-joiner steers how the scalars beside it are shaped, so it is set with them whatever the face maps, and a ligature it stands inside, as `f` and `l` in `Auf` U+200C `lage`, is not formed; a glyph another face gives for default ignorable scalars alone is set as nothing. A zero width joiner the face does not map is set as nothing, so the scalars beside it stay in the face chosen for their clusters. So a combining mark the face lacks takes its base letter to the face that has both, a kanji with a variation selector stays in the face that has the kanji, and no cluster is split over faces.
- **Fonts are part of the environment the resolved document pins** ([FRAMES-19](../FRAMES-19/SPEC.md)): every face resolve set text in, fallback faces included, is written with its hash, so text that fits a title's `width` and `lines` with the fonts it was resolved with is laid out and drawn the same on every machine it is rendered on. Resolved on a machine with other fonts, the same text is laid out with those, and it may take other lines or stop on `lines`, which is why a pack ships the fonts its templates are designed in ([FRAMES-17](../FRAMES-17/SPEC.md)).

### Spacing

- Resolve shapes each run with its style's `features`, and with the OpenType `kern` feature on for `kerning: metrics` and off for `kerning: none`. A feature the style does not set is as the font's script turns it on or off, as CSS leaves it. A feature tag the face does not have does nothing, as in CSS.
- In a run whose `tracking` is not 0 at some instant the optional ligatures (`liga`, `clig`, `dlig`) are off, unless its `features` turns them on, as CSS turns them off under `letter-spacing`, since a ligature would join characters the tracking spaces apart. A run's features are one setting over the whole run, so they are off between the letters of a cursive script in it as well, where no tracking lies (below): the required ligatures (`rlig`) and the joining forms, which make that script's words, stay on, and a run that wants its optional ligatures under tracking turns them on in its `features`.
- The shaping provider gives each glyph an advance, which moves the pen along the line, and a placement offset from the pen, as a font's GPOS table places a combining mark over its base. A glyph is drawn at the pen position with its placement offset added, and the pen moves by advances and tracking alone, so a placement offset moves the glyph it is on and nothing after it. The resolved document writes each glyph's pen position and its placement offset apart ([FRAMES-19](../FRAMES-19/SPEC.md)), and every box this spec defines from glyphs is made from the pen ([Units](#units)).
- **`tracking` is space between neighbouring characters.** Between every two characters with glyphs of their own ([Units](#units)) that are neighbours on a line as its glyphs are placed ([Direction](#direction)), but two letters of one cursive script (below), it adds `tracking / 1000 ×` the size of the run of whichever of the two comes first in the text, so it follows each character as the character is read: on its right in text read left to right, and on its left in text read right to left. A line holds none before its first character with glyphs of its own or after its last, as they are placed, and a character with none of its own has no neighbour, so a ligature that tracking leaves on, a required one such as `rlig` or one the `features` turn on, is spaced as one character, and a ligature that ends a line, whose later characters have no glyphs of their own, takes none after it. The tracking between two characters is space between the pen position where the left one's glyphs' advances end and the one where the right one's glyphs begin, which belongs to no character: the shaping provider gives advances without tracking, and resolve adds it to the pen, never to an advance. A space that hangs past a line's end ([Lines](#lines)) is no character and adds none. So the width of a line, which wrapping and `align` measure, holds the tracking between its characters and none at its ends, whatever direction they run in, and tracking does not move a centred or a left- or right-aligned line off its place. The resolved document writes each run's static tracking beside its characters' advances, and a document whose pen positions they do not give stops when it is read ([FRAMES-19](../FRAMES-19/SPEC.md#reading-a-resolved-document)).
- **No tracking lies between two letters of one cursive script**, since a cursive connection is one stroke drawn across two characters, and space put there breaks the word into pieces. So a word of a cursive script is spaced as one character: tracking lies between it and a space, a punctuation mark, a digit of another script or a letter of another script beside it, as between any two characters, and not between its letters. This is what CSS Text 3 requires of a user agent that cannot stretch a cursive word without breaking its connections ([letter-spacing](https://www.w3.org/TR/css-text-3/#cursive-tracking)). A character is a letter of a script when its first scalar has a General_Category of letter or number (L or N), as CSS takes a typographic letter unit's properties from the first scalar of its grapheme cluster, and that script is its Script value or one of its Script_Extensions values, as CSS reads a character's script, so an Arabic-Indic digit is a letter of Arabic and `ـ` (U+0640, tatweel), whose Script is Common, is a letter of Arabic, Syriac and the other scripts it extends to. A script is cursive when ArabicShaping.txt gives one of its characters the Joining_Type D (dual-joining), which needs no list of scripts and holds those CSS names (Arabic, Hanifi Rohingya, Mandaic, Mongolian, N'Ko, Phags Pa and Syriac) and those Unicode encodes after them, such as Adlam and Sogdian. The rule is by script and not by joined pair, as CSS's is: two letters of a cursive script that do not join, as `ر` before the letter after it, take no tracking either, so a word keeps one colour along it and the gaps between its words stay larger than any inside it. Two letters of different cursive scripts, which no font joins, take tracking. Scripts, script extensions and joining types are part of the environment resolve reads, as segmentation is ([Units](#units)), and the resolved document writes the cursive scripts each character is a letter of ([FRAMES-19](../FRAMES-19/SPEC.md)), so evaluation and the reading of a resolved document find the same gaps without Unicode data.
- **Keyframed `tracking` ([FRAMES-11](../FRAMES-11/SPEC.md)) keeps the line breaks resolve makes once**, since letter spacing that opens or closes is a standard title move, and outside frames it would be a title for every frame ([FRAMES-25](../FRAMES-25/SPEC.md)), while broken once at its widest the lines hold at every value it takes. **The lines are broken once for the whole motion, at the widest tracking it takes**, since the design a title draws is its motion as well as its rest: one line layout holds the whole clip, and no instant overflows it. Keyframed tracking comes only from the title's `character`, one timed value over every run, so its keyframes and eases are every run's and every run reaches its widest at the same instant. A `null` in those keyframes is each run's own tracking ([FRAMES-4](../FRAMES-4/SPEC.md)), and where the runs' own trackings lie on both sides of a keyframe's value their widest instants differ; each run is still broken at its own widest, which no instant passes. Resolve breaks the lines with each run at the largest tracking it takes over the clip's visible range, an ease's overshoot included, which the formulas of its eases give exactly ([FRAMES-4](../FRAMES-4/SPEC.md)), so no line is wider than `width` at any instant, and checks `lines` there. It places each glyph at the run's static tracking, its style's with the title's static `character` merged over it. At each instant evaluation places every glyph along its line, moved by the tracking beyond the static tracking between each two neighbouring characters left of it on that line that take tracking (for each, the tracking at that instant of the run it is taken from less that run's static tracking, `/ 1000 ×` the run's size), and places each line again by `align` on its width at that instant. A title without `width` then has a text box as wide as its widest line at that instant, which keeps its left edge, its centre or its right edge where resolve placed it, as its `align` says, so its anchor point and its position stay. So a tracking that bounces past its last keyframe bounces in full, and no line widens past the width it was broken at. Highlight and underline pieces run over their characters' glyph boxes where they are at that instant, a character's glyph box ([Units](#units)) moves as its glyphs move and keeps its width, and a unit's glyph box, its drawn extent, its box and its parts move and widen with their glyphs.
- `baselineShift` raises the run's glyphs by its length above the line's baseline, and lowers them when it is negative. Lines keep their spacing and the text box its size: a line's ascent and descent are those of its runs as if unshifted, so a raised run may reach outside the text box, and the title's drawn extent ([Units](#units)) holds it. It may take keyframes, and evaluation raises the glyphs and their characters' glyph boxes ([Units](#units)) by its value at each instant ([FRAMES-11](../FRAMES-11/SPEC.md)).

### Lines

- Lines break by Unicode line breaking (UAX #14) over the text of all runs together, at the title's `width` when it has one and at every `\n`. A title without `width` breaks only at `\n`, so each of its lines is as long as its text. A run boundary is not a break opportunity of its own. Words are kept whole as CSS `word-break: keep-all` keeps them: no line breaks between two letters, digits, ideographs or Hangul syllables, so Korean breaks at spaces and `iPhone에서` stays whole, and Chinese and Japanese also break only at spaces, punctuation and the other places UAX #14 gives outside those pairs. A word wider than `width` starts a line of its own and breaks inside where UAX #14 allows, unless its style keeps it on one line. A piece of it that still has no break opportunity stays whole on its line and widens the text box to hold it.
- The spaces that end a line hang past its end: they are not part of its width, so wrapping and `align` do not measure them. They lie on the side the line ends on, as rule L1 of UAX #9 places them ([Direction](#direction)), past its right edge in a left-to-right title and past its left edge in a right-to-left one, next to the outermost character on that side as they were set, and move as it moves at each instant, or with their line on a line with no character. A space is a grapheme cluster whose first Unicode scalar has the Unicode `White_Space` property, whatever follows that scalar in it, so a space that carries a combining mark is a space. A space is a class of line breaking, not a promise of no ink: a space mark such as U+1680, or a combining mark set alone on U+0020, as dictionaries show one, is drawn, and every glyph of a space is drawn as any character's ([Units](#units)). The `\n` that ends a line is set on no line.
- Lines are `lineHeight` apart, baseline to baseline, the clip style's with the title's `paragraph` merged over it. The glyphs of every run on a line share its baseline. The first baseline lies the largest ascent among that line's runs below the top of the text box, and the box ends the largest descent among the last line's runs below the last baseline. A line with no text, which only a `\n` makes, takes the ascent and descent of the run it begins in. A `\n` that ends the text starts such a line after it, as every `\n` starts a line, so `"Hello\n"` is two lines, the second empty, and counts as two against `lines`. In a vertical writing mode the lines are stacked along the block axis, as [Writing mode](#writing-mode) says.
- **`lineHeight` may take keyframes in the title's `paragraph`** ([FRAMES-11](../FRAMES-11/SPEC.md)), since no line break depends on it: lines break across the width alone. Resolve places the lines at its static value, the clip style's with the title's static `paragraph` merged over it, and at each instant evaluation places them at its value then: the first baseline stays, and each later line moves by the change in line height once for each line before it. The text box keeps its top edge where resolve placed it, so its anchor point and its position stay and the lines below the first move down as they open, as After Effects moves the lines of a text layer when its leading changes. Highlight and underline pieces, glyph boxes ([Units](#units)), units' boxes and their parts move with their lines.
- The text box is as tall as its lines at each instant. A title with `width` has a text box `width` wide, and a title without one has a text box as wide as its widest line, which fits the text exactly. The paragraph background, the clip style's `background` with the title's `paragraph` merged over it, lies behind the text box and grows the title's box by its padding on each side. Its `color`, `padding` and `radius` may take keyframes, and at each instant it is drawn, and grows the title's box, with their values then.
- Each line is placed inside the text box by its `align`, the clip style's with the title's `paragraph` merged over it, measured on the advances of all its runs: inside `width` when the title has one, and inside the widest line when it has none. `align` is where a line sits in the text box, against its `left` or its `right` edge or about its `center`, whatever direction the line reads in, since it is a fact of where the line is drawn. Where no layer gives it, it is the side the title's paragraph direction starts from ([Direction](#direction)), `left` for `ltr` and `right` for `rtl`, as CSS `text-align: start` sets a paragraph against the side it is read from ([FRAMES-22](../FRAMES-22/SPEC.md)).
- Resolve shapes the text with the shaping provider in shaping runs, each a stretch of one run's text at one embedding level, set in the direction of that level ([Direction](#direction)), and the provider gives glyph ids, advances and placement offsets ([Spacing](#spacing)). A run boundary and a change of embedding level each end a shaping run. frames breaks, wraps and places the lines. The resolved document carries glyph runs (font file, face, size, colour, stroke, highlight and underline pieces, glyph ids, pen positions and placement offsets) and the box they fill. A renderer draws the glyphs where they are written and shapes nothing.
- A style's `lines` is the most lines its text may take, a whole number of 1 or more. It limits a title with `width` or without one. Text that needs more lines than that, after wrapping at `width` and after every `\n`, stops, since cutting it or shrinking it to fit would show something other than what was written; a title without `width` counts the lines its `\n` make. So a line of a `lines: 1` style that is wider than the title's `width` stops, since it would need a second line. Without `lines` a title takes as many lines as it needs.

### Direction

Right-to-left and mixed-direction text is ordered by the Unicode Bidirectional Algorithm (UAX #9), as every text engine that sets Arabic and Hebrew orders it, and its terms are this section's: embedding level, paragraph embedding level, logical order and visual order. **A title's text stays in logical order everywhere but where its glyphs are placed on a line**: runs, ranges, characters, words, lines, units, the order a title animated by unit steps through them ([FRAMES-14](../FRAMES-14/SPEC.md)) and line breaking all read the text in the order it is written and read, whatever direction its characters run in, and visual order applies only where the glyphs of a broken line are placed, as UAX #9 resolves levels over a paragraph and reorders each line after lines are broken (rules L1 to L4). So a reveal by character starts an Arabic word at its first letter, on its right, a word is the same word in either direction, and every range counts the text as written.

- **The paragraph direction is a paragraph attribute**, the title's `direction` ([FRAMES-22](../FRAMES-22/SPEC.md)), one for the whole title as its `align` is: `ltr` sets every UAX #9 paragraph of its text at paragraph embedding level 0, `rtl` at level 1, and `auto` at the level rules P2 and P3 give the first of its paragraphs that holds a strong character (one of bidirectional class L, R or AL outside an isolate), or 0 when none does, as HTML's `dir="auto"` takes an element's direction from its first strong character. Every `\n` ends a UAX #9 paragraph, since a line ending is read as `\n` ([Runs](#runs)) and `\n` is a paragraph separator to UAX #9. So a title whose text holds no right-to-left character is laid out left to right whatever its `direction` says.
- Resolve finds the embedding level of every character by UAX #9, rules X1 to I2 over each paragraph at the paragraph embedding level above, in the text of all runs together, so a run boundary changes no level. The explicit formatting characters in the text (the embeddings, overrides and pop U+202A to U+202E, the isolates U+2066 to U+2069, and the marks U+200E, U+200F and U+061C) embed, override, isolate and mark as UAX #9 reads them, since they are text, and no key or markup stands in for them. **A grapheme cluster is never split over levels**: a character takes the level of its first scalar, as it takes the style of the run its first scalar is in ([Runs](#runs)). A character that rule X9 removes, an explicit formatting character or one of class BN, takes the level of the character before it in its paragraph, or the paragraph embedding level when none is, as UAX #9 retains such characters in its implementation notes. Explicit formatting characters are default ignorable, so they take no part in the choice of a face and are drawn as nothing unless a face maps them ([Faces](#faces)).
- Each shaping run ([Lines](#lines)) lies at one level and is shaped in its direction, left to right at an even level and right to left at an odd one, so a script joins, kerns and forms ligatures in the order it is read. The shaping provider gives a shaping run's glyphs in the order they lie along the line from left to right, for a right-to-left run the reverse of the order it is read in, as HarfBuzz and Core Text give them ([FRAMES-21](../FRAMES-21/SPEC.md)).
- Lines break as [Lines](#lines) says, in logical order and before anything is reordered, and each candidate line is measured as it would be placed, reordered by L1 and L2 over it, since tracking lies between neighbours as placed ([Spacing](#spacing)) and a line's width is its width as placed. Where neighbouring runs differ in tracking or size, logical order would give the same characters other gaps: `x y z` at levels 1 1 0 is placed `y x z`, with the tracking of `x` in both its gaps, where logical order would give one to `x` and one to `y`. Each line is then reordered by rules L1 to L4. L1 sets the spaces that end the line, and the other characters it names, at the paragraph embedding level, so the spaces that hang lie on the side the line ends on. L2 reverses the line's characters from its highest level down to its lowest odd one, which gives them in visual order. L3 is the shaping provider's, since a grapheme cluster is placed whole with its glyphs as the provider gives them. L4 is the shaping provider's too: a character with the `Bidi_Mirrored` property at an odd level is set in its mirrored glyph, so an opening parenthesis in Arabic text opens to the left, as OpenType's `rtlm` feature and the `Bidi_Mirroring_Glyph` property give it, and the glyph keeps the scalar of the character it was set from.
- **Glyphs are placed in visual order.** On a line, the groups of glyphs ([Units](#units)) lie in the order L2 gives their first characters, each group's glyphs in the order the shaping provider gave them, and the pen moves from the line's left end to its right end across them, by advances and tracking ([Spacing](#spacing)). Every box this spec makes from glyphs, a character's glyph box, a highlight or underline piece, a unit's boxes and a drawn extent ([Units](#units)), is made from where the glyphs lie, and every other rule reads the text in logical order. A line whose characters all lie at level 0 is placed in logical order, so text that reads left to right is laid out as it reads.
- **Bidirectional classes are part of the environment resolve reads, as segmentation is** ([Units](#units)): the classes, the paired brackets and the mirroring UAX #9 reads follow the Unicode data of the implementation that resolves, and this spec fixes no Unicode version. The resolved document writes the level each character took and the title's paragraph direction ([FRAMES-19](../FRAMES-19/SPEC.md)), and evaluation reorders by those levels alone, so one resolved document places its lines the same wherever it is evaluated. A mirrored glyph is a glyph of a pinned face, which the resolved document writes as it writes every glyph.

### Writing mode

A title's lines are set horizontally or vertically, as CSS Writing Modes Level 3 sets them, and its terms are this section's: writing mode, inline axis, block axis, line-left and line-right, line-over and line-under, block-start and block-end, upright and sideways. **A writing mode chooses the axis a line's glyphs are placed along, its inline axis, and the axis its lines are stacked along, its block axis, and nothing else**: every other rule of this spec is written in the words of horizontal text and holds in every writing mode as the table below reads its words, but for where the first line lies, which the rule of stacking below states for every mode. So runs, ranges, characters, words, lines, units, line breaking, embedding levels and visual order, tracking, hanging spaces, `align`, `lineHeight`, highlights, underlines, glyph boxes and the drawn extent are one rule each in horizontal and in vertical text, turned onto other axes, as CSS lays out every writing mode with one set of rules written in its logical terms, and a style a theme turns from horizontal to vertical keeps its look, turned with its text.

- **The writing mode is a paragraph attribute**, the title's `writingMode` ([FRAMES-22](../FRAMES-22/SPEC.md)), one for the whole title as its `direction` is, named by the values of CSS `writing-mode`: `horizontal-tb` sets horizontal lines stacked from top to bottom; `vertical-rl` vertical lines stacked from right to left, as Chinese, Japanese and Korean are set; and `vertical-lr` vertical lines stacked from left to right, as Mongolian and Manchu are set. Where no layer gives it, it is `horizontal-tb`, CSS's initial value, so a title is set horizontally unless its style or its `paragraph` asks for vertical lines, as After Effects and Premiere Pro set vertical text only with their vertical type tools, and every document laid out before this attribute is laid out as it was.
- The words of this spec name these axes, sides and lengths in each writing mode. Line-over is the right side in both vertical modes, as CSS sets it, since a glyph set sideways is turned clockwise and its ascenders point right, so the side lines are stacked toward is the line-under side in `horizontal-tb` and `vertical-rl` and the line-over side in `vertical-lr`.

| Word in this spec | Term | `horizontal-tb` | `vertical-rl` | `vertical-lr` |
| --- | --- | --- | --- | --- |
| along a line, across it from one end to the other (an advance, tracking, a line's width, a piece's or a part's span), the x of a pen position | inline axis | x, to the right | y, down | y, down |
| left, leftmost, a line's left end | line-left | left | top | top |
| right, rightmost, a line's right end | line-right | right | bottom | bottom |
| above a baseline, ascent, raised, up, a top edge | line-over | up | right | right |
| below a baseline, descent, lowered, down from a baseline | line-under | down | left | left |
| the top of the text box | block-start | top | right | left |
| the y of a baseline, a later line lying below, lines moving down | block axis, toward block-end | y, down | x, to the left | x, to the right |
| a title's `width`, the width of a text box, wide | inline size | width | height | height |
| the height of a text box, tall | block size | height | width | width |
| a padding's first value, vertical, above and below | block axis | top and bottom | right and left | right and left |
| a padding's second value, horizontal, at both ends | inline axis | left and right | top and bottom | top and bottom |

- **Lines are stacked from the block-start edge of the text box.** The first baseline lies inside that edge by the largest extent among the first line's runs on the side that faces it, and the text box ends past the last baseline by the largest extent among the last line's runs on the side that faces block-end: their ascent and their descent in `horizontal-tb` and `vertical-rl`, and their descent and their ascent in `vertical-lr`, whose block-start is its lines' line-under side. Each later baseline lies `lineHeight` toward block-end from the one before it. In `horizontal-tb` this is the rule of [Lines](#lines) word for word, and it is the one rule there whose words the table cannot read alone, since the side a line turns to the top of its box is its line-over side only where line-over faces block-start. In every mode it is how CSS stacks line boxes, each with its over side where its glyphs put it, so Mongolian lines stack from the left with their ascenders to the right.
- **In a vertical line the baseline is the central baseline**, which CSS takes as the dominant baseline of vertical text under `text-orientation: mixed`, and it lies halfway between a face's ascent and descent, where CSS assumes it lies in a font that gives none, since frames reads a face's ascent and descent and no baseline table, in vertical text as in horizontal. So in a vertical line a run's ascent and descent, its extents on the line-over and line-under sides of the baseline, are each half the sum of its face's ascent and descent at its size, and its alphabetic baseline lies half its face's ascent less its descent from the line's baseline on the line-under side. Where a run falls back to other faces, a sideways glyph sits on the alphabetic baseline of the face that sets it, and the run's underline on the alphabetic baseline of the run's own face, the face its highlight piece reads. In a horizontal line the baseline is the alphabetic baseline, and a run's ascent and descent are its face's. Every rule that reads a run's ascent and descent reads these, a line's place, a glyph box and a highlight piece among them, so a vertical line is as wide as its runs' faces are tall.
- **In a vertical line each character is set upright or sideways by its Vertical_Orientation**, the property of Unicode Vertical Text Layout (UAX #50), as CSS `text-orientation: mixed` sets it: a character whose value is U, Tu or Tr is set upright, in glyphs frames does not turn, and one whose value is R is set sideways, turned 90 degrees clockwise. **A grapheme cluster is never split over orientations**: it takes the orientation of its first scalar, and one that holds an enclosing mark (General_Category Me) is upright, as UAX #50 orients a cluster, since a mark turned apart from its base would leave it. So ideographs, kana, Hangul and the fullwidth forms stand, and Latin letters, digits, Arabic, Hebrew and Mongolian lie on their sides, and a writer who wants a Latin letter or a digit upright writes its fullwidth form, as Japanese text writes it. In a horizontal line no character is turned.
- A change of orientation ends a shaping run ([Lines](#lines)), as a change of level does, so a shaping run is a stretch of one run's text at one level and one orientation. An upright shaping run is shaped in its face's vertical layout, as the shaping provider sets vertical text, in the vertical forms its face's `vert` feature gives, with the vertical positioning features its face or the style's `features` turn on, and each glyph with its vertical advance: so the ideographic comma and full stop sit at the top right of their cells, the corner brackets turn and the prolonged sound mark runs down the line. Its glyphs are the forms its face and the provider give in that layout, which may be turned forms the face itself draws, as a face's `vrt2` turns some symbols where a provider applies it with `vert`: frames promises that it does not turn an upright run, not that its face draws no turned form. A sideways shaping run is shaped as horizontal text, in the direction of its level, and its glyphs are turned. A style's `features` apply to both as they do in horizontal text ([Spacing](#spacing)), so `"vert": 0` keeps the horizontal forms upright and `"vpal": 1` sets proportional vertical metrics, as CSS `font-feature-settings` sets them.
- **An upright glyph's vertical metrics are its face's, made from its ascent and descent where the face has none.** Its vertical advance is the one its face's `vmtx` table gives, and its vertical origin lies half its horizontal advance across from its horizontal origin and, above it, at the height its face's `VORG` table gives, or without one at its `vmtx` top side bearing above the top of its outline, as OpenType places it. In a face without a `vmtx` table an upright glyph's vertical advance is the face's ascent plus its descent and its vertical origin lies its ascent above its horizontal origin and half its horizontal advance across, so it is set in the box the face sets it in on a horizontal line, turned along the vertical one. CSS requires metrics to be made for a face that lacks them and defines no way to make them, and OpenType defines none, so frames fixes them, and two shaping providers set such a face the same way.
- The pen of a vertical line moves along its baseline from the line's line-left end, by advances and tracking ([Spacing](#spacing)). An upright glyph is set with its vertical origin at the pen, so it stands centred on the line, and a sideways glyph with its horizontal origin on its run's alphabetic baseline. A glyph's placement offset runs from the pen to its origin, the point its outline is drawn from, so it holds the move to the glyph's vertical origin, or to its run's alphabetic baseline, beside what its face's positioning gives it, and every glyph in every writing mode is drawn from its origin at its pen position plus its placement offset, standing or turned 90 degrees clockwise about that origin ([FRAMES-19](../FRAMES-19/SPEC.md), [FRAMES-20](../FRAMES-20/SPEC.md#glyphs-and-adjustments)). Boxes are made from the pen and the advances ([Units](#units)), so in vertical text too a placement offset moves no box.
- [Direction](#direction) holds in every writing mode. A line's visual order runs from its line-left end to its line-right end, from top to bottom in a vertical line, so a word of Arabic or Hebrew set sideways at an odd level reads from the bottom up, as CSS lays out Arabic turned clockwise, upright characters at an odd level are placed in the same reversed order, and an `rtl` title's lines start at their bottom ends, where its default `align`, `right`, sets them.
- **Vertical orientations are part of the environment resolve reads, as bidirectional classes are** ([Direction](#direction)): they follow the Unicode data of the implementation that resolves, and this spec fixes no Unicode version. The resolved document writes the title's writing mode and, for each glyph run, whether its glyphs are turned ([FRAMES-19](../FRAMES-19/SPEC.md)). Evaluation places glyphs and boxes by the pen and the advances alone and reads no orientation, and a renderer turns the glyphs of the runs written turned, so one resolved document places and draws its glyphs the same wherever it is evaluated.

### Highlights and underlines

A run's highlight and its underline mark the run where it lies, as a highlighter and an underline do on a page. They are drawn on each line the run occupies, as one piece for each stretch of the run's characters that lie side by side on the line as placed ([Direction](#direction)), each piece with its own padding and rounded corners, as CSS `box-decoration-break: clone` draws an inline box broken over lines and split by bidirectional reordering. So a run whose characters on a line lie at one level is one piece there, and a run that holds both directions may be several pieces on one line, where the text of another run lies between its parts as they are placed.

- A run's characters on a line are those set in its glyphs there, a character with no glyph of its own being of the run of its group's first character, whose glyphs it is drawn with ([Units](#units)), as a resolved document tells a piece's characters by their glyph runs ([FRAMES-19](../FRAMES-19/SPEC.md)). So an isolate initiator that no face draws, opening a run after another run's space, is of that space's run. A piece runs across the line from the left edge of the glyph box ([Units](#units)) of its leftmost character to the right edge of the glyph box of its rightmost one, the characters a fallback face set included. The spaces inside the run are characters and lie in it, and the spaces that end a line are no character and lie outside it.
- A highlight piece runs from the run's ascent above the baseline to its descent below it, the ascent and descent of its face at its size, as CSS paints an inline box's content area. It grows by its `padding`, vertically above and below and horizontally at both ends, and its corners are rounded by its `radius` ([FRAMES-20](../FRAMES-20/SPEC.md)).
- An underline piece is a band across the piece, without padding, `width` thick, its top edge `offset` below its run's alphabetic baseline, which in a horizontal line is the line's baseline and in a vertical line lies on the line-under side of it ([Writing mode](#writing-mode)), in its `color`. A `true` underline takes the leaves below it, and a key that no layer gives takes the thickness and the position of the top edge from the face's `post` table at the run's size, and the run's colour ([FRAMES-22](../FRAMES-22/SPEC.md)). It is drawn through descenders, as CSS `text-decoration-skip-ink: none` draws it.
- Both move with the run's `baselineShift` at each instant. A highlight's `padding` and `radius` and an underline's `width` and `offset` may take keyframes ([FRAMES-11](../FRAMES-11/SPEC.md)), and each piece is drawn with their values at each instant.
- Neither takes part in layout: they move no glyph, add no space and do not grow the text box, so a padded highlight may reach over the space beside its run and out of the text box. A title's drawn extent holds them ([FRAMES-6](../FRAMES-6/SPEC.md), [FRAMES-14](../FRAMES-14/SPEC.md)).
- They are drawn over the paragraph background and under every glyph: the highlights in text order, each piece at the place of its first character in the text, then the underlines, then the glyphs' strokes and fills ([FRAMES-20](../FRAMES-20/SPEC.md)).

### Units

A title's laid out text is split into characters, words and lines, in reading order, which is the order of its text, and a title whose animation plays by character, word or line ([FRAMES-14](../FRAMES-14/SPEC.md)) moves them as its units.

| Name | Meaning |
| --- | --- |
| `character` | an extended grapheme cluster of UAX #29 |
| `word` | a word between UAX #29 word boundaries, with the punctuation it touches |
| `line` | a laid out line |

- A line's characters are its grapheme clusters up to the last one that is not a space, the spaces inside it included. The spaces that hang past its end ([Lines](#lines)) are no character, and a line that holds nothing but spaces, such as an empty line a `\n` makes, has none: all its spaces hang.
- A piece of text between two UAX #29 word boundaries that holds a letter, a digit or an ideograph is a word. A piece of punctuation or symbols joins the word it touches with no space between them, the word before it when it touches two, so `Hello,` and `"Quote"` are one word each, and a dash between two spaces is a word of its own. The boundaries are those of UAX #29's default rules, with no dictionary, so each Chinese or Japanese ideograph is a word, a Korean word runs from space to space, and `iPhone에서` is one word. A space is in no word. A word is the word as written: one a line breaks inside ([Lines](#lines)) is still one word.
- **Segmentation is part of the environment resolve reads, as fonts are** ([Faces](#faces)): grapheme clusters and word boundaries (UAX #29) and line break opportunities (UAX #14, [Lines](#lines)) follow the Unicode data of the implementation that resolves, and this spec fixes no Unicode version. The resolved document writes what they gave, its characters, words, lines and units ([FRAMES-19](../FRAMES-19/SPEC.md)), so two resolves with different Unicode data may split a text differently, as Unicode 15.1 changed the grapheme clusters of Devanagari conjuncts, and one resolved document is split the same wherever it is evaluated.
- **Glyphs are assigned to characters by one rule**, which covers ligatures and the scripts whose shaping moves a glyph across characters, as Devanagari moves a reph or a pre-base form. The shaping provider gives each glyph the scalar of the text it was set from ([FRAMES-21](../FRAMES-21/SPEC.md)), and each glyph is taken with the character that scalar is in. On a line, the glyphs of each shaping run, taken in the order it is read, from its left end at an even level and from its right end at an odd one ([Direction](#direction)), are cut into groups where that character changes, and neighbouring groups of the run are merged until every character of a group comes before every character of the next, so the groups of the line lie in increasing text order. A group's first character is the first in the text that its glyphs are taken with, and the group's glyphs belong to it. A line's characters are cut into its groups at the first character of each group but the line's first, so a group holds the characters from its first up to the next group's first in the text, and the line's first group also those before its first, which no cut sets apart, as an isolate initiator that no face draws comes before the first word of a line it opens. Every character of a group but its first has no glyph of its own: its glyph count and its advance are 0, it shares the glyph box of the group's first character, and it is drawn with that character, a space or not. A ligature is the case of one glyph, as `ffi` sets three characters in one glyph in `office` and `lam` with `alef` set two in one glyph in Arabic, and a character is never joined to another.
- Each character, word and line has a range of the title's text, `[start, end)` counted in Unicode scalars over the title's text, the text of its runs joined in order ([Runs](#runs)). A character's range and a word's hold their scalars. A line's range runs from the start of its first character's range to the end of its last one's, and a line with no character has the empty range where it starts: at the first scalar set on it, or, for a line nothing is set on, where the text after the line before it starts, the scalar after the `\n` that ends that line, and 0 for the first line, so the empty first line of `"\nHello"` has the range `[0, 0)`. So the spaces that hang past a line's end and the `\n` that ends it are in no line's range.
- **Where text lies is a fact of its characters and its lines.** A character's glyph box is the one box made from glyphs, and a unit's glyph box, a highlight or underline piece ([Highlights and underlines](#highlights-and-underlines)), a part and a drawn extent (below) are made from glyph boxes. It is a fact of the pen, not of where its glyphs are drawn: it starts at the pen position where its glyphs begin on its line and is as wide as the sum of their advances, whatever placement offsets they are drawn with, the tracking beside it left out ([Spacing](#spacing)). It runs down its line from its baseline less the line's ascent to its baseline plus the line's descent, the largest ascent and descent among the line's runs, and its baseline is the line's baseline raised by its run's `baselineShift`. A character with no glyph of its own has the glyph box of its group's first character, so the characters of a ligature share its box. A space that hangs past a line's end, which is no character, has a glyph box made the same way. A title's **drawn extent**, a name this spec gives, is its text box grown to hold the glyph boxes of everything it draws, its characters and the spaces that hang past its lines' ends, so a run raised outside the text box lies inside it: it is what a title's reveal wipes and what `bounds` and `locate` take of its glyphs ([FRAMES-14](../FRAMES-14/SPEC.md), [FRAMES-20](../FRAMES-20/SPEC.md#glyphs-and-adjustments)). A line has one place whatever units animate its characters: its baseline, unshifted, and its ascent and descent ([Lines](#lines)), so a line with no character has a place too. A word lies where its characters lie and has no place of its own. Glyph boxes and lines lie in the text box, and at each instant a character's glyph box is its box at the static values moved as its glyphs move then, and a line lies at its baseline then ([Spacing](#spacing), [Lines](#lines)), so a character's box is the same for the same drawn glyphs whether the tracking takes keyframes or not.

Under `by`, the units are the title's characters, words or lines, in reading order, except that:

- Spaces are not units. Each space goes with the unit before it on its line, or with the line's first unit when none is before it, and it is none of the characters that unit holds. So a `line` unit holds its line's characters but its spaces, which go with it, and a line that holds nothing but spaces, which has no character, is no `line` unit.
- **Every glyph is drawn by one unit.** A unit draws the glyphs of every character that goes with it, its spaces included. The spaces that hang past a line's end are drawn by the line's last unit, and those of a line with no unit, which holds nothing but spaces, by the unit before them in reading order, or by the title's first unit when none is before them. A title with no character has no unit and is drawn as a title not animated by unit ([FRAMES-20](../FRAMES-20/SPEC.md#glyphs-and-adjustments)). So a title by unit at rest draws every glyph it draws without `by`.
- A unit does not cross a line: under `word`, a word a line breaks inside is a unit on each line.
- Under `word`, a character that is neither a space nor in a word, such as a word joiner (U+2060) between two spaces, is held by the unit before it on its line, or by the next when none is before it.
- A character that is not a space, on a line that would hold no unit, is a unit of its own, as a word joiner alone on a line is under `word`. So every character goes with one unit on its line, and the characters that go with a unit, those it holds and the spaces that go with it, are one stretch of its line in reading order. The resolved document writes that stretch for each unit, and the lines whose hanging spaces it draws ([FRAMES-19](../FRAMES-19/SPEC.md)), and evaluation assigns no character or glyph to a unit.
- Units that the characters of one group of glyphs (above) go with are one unit, since the group's glyphs are drawn with its first character. Under `character` the optional ligatures (`liga`, `clig`, `dlig`) are off, unless the style's `features` turns them on, so that each character can move alone.
- A unit's glyphs are the glyphs it draws. Its glyph box, which places its motion ([FRAMES-14](../FRAMES-14/SPEC.md#by-character-word-or-line)), is the smallest box that holds the glyph boxes of the characters it holds with their `baselineShift` left out, from the leftmost left edge among them to the rightmost right edge and down its line, from the line's baseline less the largest ascent among the line's runs to the baseline plus their largest descent. A unit's box is its glyph box grown on every side by half the widest stroke among its glyphs, and then to hold the parts of highlights and underlines it carries (below) at the largest padding, underline `width` and `offset` their keyframes give. Both lie in the text box and do not move with `baselineShift`, so the units of a line that carry no highlight share the line's height and its centre. A unit whose characters lie apart on its line as they are placed, as a word set across a change of direction may, has one glyph box over all of them, since it moves as one unit. A unit's **drawn extent** is the smallest box that holds the glyph boxes of everything it draws, the characters that go with it and the hanging spaces it draws, each with its `baselineShift`: it is where the unit's glyphs lie, which its reveal wipes and which `bounds` and `locate` take ([FRAMES-14](../FRAMES-14/SPEC.md#by-character-word-or-line), [FRAMES-20](../FRAMES-20/SPEC.md#glyphs-and-adjustments)), while its glyph box places its motion, so a raised character is not cut and the units of a line keep one centre.
- The paragraph background is not part of any unit. A run's highlight and underline are drawn with the units whose characters they mark, so they enter and leave with their words. Each piece ([Highlights and underlines](#highlights-and-underlines)) is cut into parts wherever two of its characters that are neighbours as placed go with different units, at the left edge of the glyph box of the right one: a part runs over a stretch of the piece's characters that go with one unit, the spaces among them, and is that unit's, so a unit carries one part of a piece, or several where its characters lie apart in it, and the leftmost and the rightmost part reach to the piece's ends, its padding included. A part is the piece as drawn whole, with its padding and rounded corners, cut to the part's span across the line, so once every unit has entered and before any leaves, the title draws as it does without `by`, at any opacity, blend, mask or track matte of the title, since its units are composited as one group ([FRAMES-20](../FRAMES-20/SPEC.md)). Every character of a piece goes with a unit on its line, so every piece is drawn by units, each part on its line, and a title by unit at rest draws as it does without `by`.

## Interactions

Styles are [FRAMES-22](../FRAMES-22/SPEC.md). A title's keys, `width` among them, are [FRAMES-11](../FRAMES-11/SPEC.md). The shaping provider is [FRAMES-21](../FRAMES-21/SPEC.md), and it takes a shaping run's direction and gives its glyphs in the order they lie on the line. The resolved document writes each title's paragraph direction and each character's level as [FRAMES-19](../FRAMES-19/SPEC.md) says, and `evaluate` reports them as [FRAMES-23](../FRAMES-23/SPEC.md) says. A box child that is never mirrored keeps reading in the direction it was set ([FRAMES-10](../FRAMES-10/SPEC.md)). The writing mode is a paragraph attribute of [FRAMES-22](../FRAMES-22/SPEC.md) that a title's `paragraph` sets ([FRAMES-11](../FRAMES-11/SPEC.md)), the shaping provider takes whether a shaping run is set upright in a vertical line ([FRAMES-21](../FRAMES-21/SPEC.md)), and the resolved document, the display list and `evaluate` write the writing mode and the turned glyph runs as [FRAMES-19](../FRAMES-19/SPEC.md), [FRAMES-20](../FRAMES-20/SPEC.md) and [FRAMES-23](../FRAMES-23/SPEC.md) say. Placement names, anchor points and a reveal's `revealFrom` name sides of a box and of the frame, not of a line ([FRAMES-1](../FRAMES-1/SPEC.md), [FRAMES-14](../FRAMES-14/SPEC.md)), so they do not turn with the writing mode: a vertical caption is placed `right` by its placement, and a reveal down its lines wipes from `top`. Pack fonts are found as [FRAMES-17](../FRAMES-17/SPEC.md) says. A title's box is measured into a content-fit frame as [FRAMES-6](../FRAMES-6/SPEC.md) says.

## Alternatives considered

Inline markup (Markdown's `**...**`, a subset of HTML): it needs an escape for its own characters, it reaches only the looks its syntax names, and an agent writing text from a transcript or a script would have to quote it. Runs name any theme style and hold text as it is.

A default `width` taken from the frame: a title's box would change with the frame it is drawn on, a background could not hug a short title without its own `width`, and a content-fit frame has no width yet to take it from. A title without `width` is point text and a title with it is paragraph text, as After Effects makes them.

Highlights and underlines that take space, as CSS padding on an inline box widens its line: a highlight added to one word would rewrap the paragraph and move every word after it, where an editor adds a highlight to a caption that is already timed and placed.

Paragraph attributes per run (a run with its own alignment or line height): one paragraph has one alignment and one line spacing in every NLE title tool, and a second paragraph that needs another look is a second title. A title sets its own over its style's through `paragraph`, as After Effects' Paragraph panel sets them on a text layer.

Synthesised bold and slanted italic, as CSS `font-synthesis` and After Effects' Faux Bold and Faux Italic make them: a renderer would have to embolden or shear outlines its font does not hold, and two renderers would draw them differently. A family's own faces are what a type designer drew, and a style that asks for a slant its family cannot give is set upright, as CSS sets it under `font-synthesis: none`.

Optical kerning, as After Effects and InDesign offer it: it is each tool's own algorithm, with no formula two implementations could share. `metrics` is the font's own kerning, which every shaper reads the same.

Lines broken at the static tracking, the title stopping where any instant of a keyframed tracking overflows `width`: a name that fits at rest and overflows during a tracking-in entrance would stop there as well, so the rest layout would buy a template nothing, and lines broken again at the instants they overflow would jump from one layout to another during the move, which is no layout. Breaking once at the widest tracking keeps one layout over the whole clip, at a cost: the settled title keeps the breaks of its widest instant, and a name that `lines` accepts at rest can stop under a tracking-in entrance.

Optional ligatures kept between the letters of a cursive script in a tracked run, as CSS keeps them wherever the spacing in effect is 0: features would be set over parts of a run, which the shaping provider would take as ranges, for a stylistic form that a style can turn on by name. The connections and the required ligatures are never turned off.

Tracking after the last character of a line, as CSS `letter-spacing` adds it: a centred line would sit half a tracking step to the left of its centre, and a right-aligned one would end short of its edge.

Scripts whose shaping moves glyphs across characters left out: Devanagari and the other Indic scripts are titled in every NLE, and the groups that merge until they lie in text order give every glyph one character at no cost to the scripts that move none, where each platform's shaper reports reordered glyphs in its own way.

A unit's glyph box, a highlight or underline piece and a part made from where glyphs are drawn, from the drawn origin of the first glyph to the end of the last one's advance: a combining mark drawn back over its base, as a tilde is set over a `q` that has no precomposed form, would end the box at the mark's drawn origin, so the unit of that `q` would be narrower than its character and its reveal would cut the letter. Made from characters' glyph boxes, which are the pen's, a piece and a part hold every character they are made of, and a unit's glyph box holds the characters it holds as they lie unshifted, which its drawn extent grows to where they are raised.

A character on a line with no unit joining a unit of the line before or after it: the unit would cross a line, and its glyph box, which runs down one line, would have no place. A unit of its own keeps every unit on one line and leaves no character without a unit.

A Unicode version fixed by this spec for UAX #29, UAX #14 and UAX #9: an implementation would carry segmentation and bidirectional tables of its own in place of its platform's text data, which follows the platform's Unicode version, where what a result needs fixed is what the segmentation and the levels gave, which the resolved document writes, as it writes what a font gave.

A space that draws no glyph, as a class of ink: a space mark such as U+1680 and a combining mark set alone on U+0020 have ink, which only a glyph's outline shows, and evaluation opens no font. A space is a class of line breaking, and its glyphs are drawn by the unit it goes with.

One box for a unit's motion and for what it draws: left without `baselineShift` it would cut a raised character as its unit is revealed and leave its `rect` outside its item's `bounds`, and with `baselineShift` it would move the centre a shifted unit turns about off its line's. The glyph box places the motion, and the drawn extent holds what is drawn.

The line endings other than `\n` taken as UAX #14 mandatory breaks, each rule written for all of them: CR LF is one grapheme cluster whose first scalar is white space, so it would also be a space that hangs, and every rule that names what ends a line would name a set. Read as `\n` once, one character ends a line.

A fallback face that has every scalar of a cluster, default ignorables included: a variation selector or a joiner, which a face maps in a table of its own or not at all, would send a kanji with a variation selector, or an emoji sequence, out of the face that sets it.

Visual order kept above drawing, the characters, words and units of a line taken from left to right: a reveal by character would start an Arabic word at its last letter and a typewriter would type it backwards, a word set across a change of direction would be two words, and the ranges an extension reads would no longer count the text it wrote. UAX #9 keeps the text in logical order and reorders only a broken line, and a caption is timed in the order it is read.

Embedding levels left to the shaping provider, as Core Text and DirectWrite resolve them when they set a line: a provider resolves levels over the text it is given, a shaping run in one face and one style, so where a run or a fallback face splits the text would change how a number or a parenthesis between two words is ordered, and each provider would order a line its own way. Resolve finds the levels once over the whole paragraph, as UAX #9 asks, writes them, and hands the provider runs of one direction.

The direction of each UAX #9 paragraph found apart, as P2 and P3 find it and as CSS `unicode-bidi: plaintext` does: a title has one set of paragraph attributes and one `align`, so a two-line lower third with a name in English and its Arabic below it would have a default `align` that differs from line to line. A title's `auto` takes one direction from its first strong character, as HTML's `dir="auto"` does for an element.

`ltr` as the default `direction`, as CSS's initial `direction` is: an Arabic title would read left to right, its punctuation on the wrong side, until its writer knew the key, while `auto` gives what UAX #9 gives with no higher protocol and lays out every left-to-right text as `ltr` would.

Logical alignment names, CSS's `start` and `end`, beside or in place of `left` and `right`: where a line sits is a fact of drawing, which the physical names say once for every direction, and a style that wants the side its text starts from leaves `align` out, which takes that side ([Lines](#lines)).

A direction or an embedding on each run, as HTML sets `dir` on a span: it would be markup over what the explicit formatting characters already say in the text, which UAX #9 reads, and a run is a look, not a unit of direction.

Tracking after each character in the order it is read, on its right in left-to-right text and on its left in right-to-left text, with none after a line's last character: where the direction changes on a line, the characters on both sides of one place on the line would both add theirs there, and the line's last character in the text, which need not stand at either end of the line, would leave another place with none. Tracking taken between neighbours as placed spaces every pair once, and in text of one direction it is the same as tracking after each character.

Tracking turned into cursive elongation in a cursive script, a word stretched by kashida, the tatweel (U+0640) or a font's longer joining forms to the width the tracking would give it, which CSS Text 3 allows a user agent that can do it: where elongation goes in a word, and how far, depends on the letters, the word's place in the line, the face and calligraphic taste, which CSS itself leaves to each user agent and calls non-interoperable, and a stretched letter is a glyph no shaping provider gives for a tracking value. Spacing no two letters gives the same result in every implementation, and an author who wants a stretched word writes its tatweels as text.

Tracking only between two letters of a cursive script that do not join, as the Joining_Type of the two says, or as the shaping provider's glyphs show: the gaps would fall inside words wherever a right-joining letter such as `ر` or `و` ends a connected piece, so a word would be cut into uneven pieces and the gaps inside it would look like the gaps between words, which CSS Text 3 shows as a wrong rendering. A rule read from the glyphs would also differ with each font.

A cursive script decided by CSS Text 3's list of seven scripts: the list is of Unicode 6.0, and CSS asks user agents to extend it as Unicode encodes more. A dual-joining character in ArabicShaping.txt gives every cursive joining script of the Unicode data resolve reads, from Unicode data alone.

The gaps that take no tracking written into the resolved document, one flag for each character's gap on its left as placed: the gap is a fact of two characters and of where L2 places them, which the document already gives, and each character's cursive scripts are a fact of the character, as its level is, from which the reader and evaluation find every gap by the same rule resolve placed the glyphs by.

One highlight piece for each line a run occupies, from its leftmost character to its rightmost: where the run holds both directions, it would cover the text of another run that lies between its parts on the line. One piece for each stretch the run lies in side by side is what CSS draws for an inline box split by bidirectional reordering.

A unit cut where its characters lie apart, a word set across a change of direction made two units: the unit would no longer be the word as written, and a reveal by word would play one word as two. A unit's glyph box holds all its characters, and its parts are cut where its characters are.

Rules written for each writing mode apart, a vertical line with its own wrapping, alignment, spacing and boxes: two sets of rules would have to be kept the same wherever they mean the same thing, and each would drift where the other was changed. CSS lays out every writing mode with one set of rules in logical terms, and the table that reads this spec's words on the axes of each mode does the same with one table.

A `height` key for the length a vertical title's lines wrap at, as After Effects draws a vertical paragraph's box with a width and a height: a title's writing mode comes from its style, which a theme gives, so the key a document had to write would change with a value in another layer, and a theme that turned a style vertical would stop every document that wrote `width`. `width` names the inline size, as CSS `inline-size` names it in every writing mode, so a document keeps its keys when its theme turns its text.

`top` and `bottom` beside `left` and `right` in `align`, for vertical lines: a style's `align` would have to change with its writing mode for the same reason. CSS reads `text-align: left` and `right` as line-left and line-right in vertical modes, which are the top and the bottom.

Paddings on the physical sides, as the CSS `padding` shorthand sets them in every writing mode: a lower third's box, thin above and below its text and wide at its ends, would turn into a column box wide across the column and thin at its ends, and a highlight would do the same. The first value is the block axis and the second the inline axis, as CSS's logical `padding-block` and `padding-inline` follow a writing mode, so a look turns with its text.

`sideways-rl` and `sideways-lr`, the writing modes of CSS Writing Modes Level 4 that turn horizontal lines onto their sides: they set every glyph as in horizontal text and turn the whole box, which a horizontal title turned by 90 degrees by its `rotation`, clockwise or counterclockwise, already is.

A text orientation option, CSS `text-orientation: upright` or `sideways`, as After Effects' Standard Vertical Roman Alignment turns Latin letters upright or sideways: setting every character sideways is a horizontal title turned, as above, and setting Latin letters and digits upright is what their fullwidth forms, whose Vertical_Orientation is U, do as Japanese text writes them. CSS's `upright` also treats every character as left to right for bidirectional reordering, a second rule of order this spec would carry for what the text already says.

Horizontal-in-vertical, tate-chu-yoko, CSS `text-combine-upright`, as After Effects' Tate-Chu-Yoko sets two or three digits side by side in one cell of a vertical line: it is not a choice of axes but a new unit of layout, a stretch of characters set horizontally and fitted to one cell, which needs an attribute on a run and a fit to one em, by the face's half-, third- and quarter-width forms where it has them and by narrowing the glyphs where it does not, as CSS requires, and no renderer draws a glyph narrowed now. It is left to a later change, which these rules leave room for: a combined cell is a group of glyphs whose characters share one glyph box, as a ligature's characters do ([Units](#units)), placed in its line as an upright character is.

A Tr character set sideways where its face has no vertical form, as UAX #50 gives its fallback: whether a face has the form is known only after shaping, in the face the cluster fell back to, so the shaping provider would report each such glyph and resolve would shape it again, for a case CSS does not expect a user agent to handle and that a face which carries kana and CJK punctuation does not present.

The central baseline taken from a face's `BASE` table, or from its em box with its ascent and descent scaled to one em, as CSS Inline 3 synthesises it: frames reads no baseline table in horizontal text, where every line's baseline is the alphabetic one its faces give, and halfway between a face's ascent and descent, the edges every other rule reads, gives a vertical line that is symmetric about its baseline and as wide as its faces are tall.

Sideways glyphs taken from the face's `vrt2` feature, its own turned forms, in place of glyphs turned by frames: only some faces carry them, so a word would turn in one face and not in its fallback. frames turns every sideways glyph itself, in every face alike. Keeping the `vrt2` forms out of an upright run, where a provider applies them with `vert` and no feature setting tells the two apart, would mean applying a face's substitutions apart from the provider, and losing the vertical positioning it gives, so an upright run takes the forms of its face's vertical layout.

An underline on the right of a vertical line where the text is Japanese or Korean, as CSS `text-underline-position: auto` may choose by language: frames knows no language of a title, and the line-under side is the side the axes give and the side Chinese sets a line on. A negative `offset` sets the band on the line-over side.

A writing mode on each run, a vertical stretch inside a horizontal line: a line has one inline axis, and CSS sets an inline element of another writing mode as a block of its own inside the line. A title has one set of paragraph attributes, as it has one alignment and one line height (above).

The Vertical_Orientation of each character written into the resolved document, as its level is: evaluation reads no orientation, since boxes are made from the pen and the advances, and a renderer needs only whether a glyph is turned, which is a fact of its glyph run. What the Unicode data gave is written where it is read.
